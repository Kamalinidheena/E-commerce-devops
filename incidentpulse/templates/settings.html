💡 Deep Dive: Endpoint Availability vs. Complete Workflow Health

A primary design goal of IncidentPulse is to emphasize that HTTP socket availability does not equate to business transaction correctness.

What Endpoint Health Confirms:

  • DNS resolution succeeds for the domain.
  • TCP handshake completes within the timeout limit.
  • TLS certificate handshake is valid.
  • HTTP server responds with the expected status code (e.g. 200 OK).
  • HTTP response time meets performance expectations.

What Endpoint Health Does NOT Prove:

  • User authentication databases or OAuth flows are operating correctly.
  • E-commerce shopping cart checkout or Stripe/PayPal payment gateways work.
  • Async workers (Celery, Redis queues, RabbitMQ) are processing jobs.
  • Third-party microservice dependencies or ERP syncs are responding accurately.

🛡️ Security Architecture & SSRF Protections

Allowing user-specified health check URLs is inherently security-sensitive. IncidentPulse enforces strict server-side request forgery (SSRF) mitigations:

🔒 Scheme & Credentials

Only HTTP and HTTPS are permitted. Embedded URL credentials (e.g. user:pass@host) are rejected.

🌐 Private & Metadata Blocking

All resolved IP addresses are checked against RFC 1918, link-local, loopback, and cloud metadata (169.254.169.254).

🔄 Safe Redirect Revalidation

Redirects are resolved step-by-step; each redirect target is re-validated through the full SSRF filter before connecting.

🧪 Authorized Demo Mode

Local loopback monitoring is permitted ONLY when explicitly authorized per-service on designated hackathon ports (5000-9999).
